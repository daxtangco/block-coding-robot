Program by snapping blocks Teachable vision Works fully offline

Open: we built a low-cost, 3D-printed 5-DOF robotic arm for secondary-school robotics education. Students program it by dragging blocks, it sees objects with a camera, and sorts them. Guiding idea: the camera SEES, the PC THINKS, the arm ACTS.

In one sentence

The camera sees, the PC thinks, and the arm acts.

SEES ESP32-CAM (or laptop webcam) captures a frame
→
THINKS YOLOv8n on the PC detects & classifies the piece
→
ACTS ESP32 arm moves over WebSocket to sort it

Each capability lives on the device best suited to it — a deliberate split.

Why split it? The ESP32 is too weak for a neural net; the laptop can't ride a moving arm. Vision on the PC, motion on the microcontroller, talking over the arm's own WiFi.

The problem

  • Cost & access — commercial educational arms start around PHP 8,500–17,000+, out of reach for many schools.
  • Programming barrier — most platforms need real coding; beginners can't start.
  • Rigid perception — fixed object sets; students can't teach it their own objects.
  • Infrastructure — many depend on home WiFi or cloud accounts, awkward in class.

Our answer

A 3D-printed, hobby-servo 5-DOF arm + a block-coding IDE + YOLOv8 vision + a Grade 7–10 curriculum, running fully offline on the robot's own WiFi — built for ≤ PHP 3,500.

The PHP 8,500 / 17,000 figures are the real commercial comparators from Table 6.5 (LEWANSOUL xArm 1S and Dobot Magician Lite). Our cost ceiling target was PHP 3,500 (SO1).

The arm is the WiFi access point (SSID RobotArm-XXXX from its MAC). Laptop/phone AND the camera join THAT network. 192.168.4.1 = arm; camera auto-takes 192.168.4.50. No home WiFi, no cloud — this is what makes it classroom-deployable (SO addressed in 6.6).

The hardware

  • 5-DOF: base, shoulder, elbow, wrist, gripper
  • Open-source Thingiverse design (thing:3039476)
  • 12 printed parts, Esun PLA+ @ 20% infill
  • Base/shoulder/elbow: MG996R servos ×3
  • Wrist/gripper: MG90S micro servos ×2
  • PCA9685 16-ch PWM driver (I²C: SDA 21 / SCL 22)
  • Dedicated 5V/3A supply — servos isolated from ESP32

Why a separate servo driver + supply?

Offloading PWM to the PCA9685 frees the ESP32; isolating servo power on its own 5V/3A rail stopped current surges from resetting the board (see the optimization log). Per-joint travel caps {180,180,180,90,90} keep every servo inside its mechanical range.

Exact from Chapter 5/6: MG996R (metal-gear standard) for the three heavy joints, MG90S for wrist and gripper. Do NOT say SG90 — the paper specifies MG996R + MG90S. The isolated 5V/3A rail and PCA9685 offload are both documented fixes, not decoration.

Block-coding & manual control — SO2 ✓

Blocks snap like LEGO, type-checked by shape:

move to poseopen/close clawwait

camera sees…foreverif / else

Manual UI: ESP32 hosts an embedded page at 192.168.4.1 — joint sliders + Manual/Auto + Reset, over WebSocket (persistent, no per-request HTTP). Latency is bounded only by the local WiFi link — no cloud hop.

Gripper uses three tuned presets — open 30° / close-narrow 10° / close-wide 13° — shared by the robot page, Teach Poses, and programs. The live runner even auto-sizes the close angle by detected piece width (1-stud → narrow, 2-stud → wide).

Two run modes: compile to C++ & flash, OR run live in the browser (interpreter drives the arm over the same WebSocket — instant iteration).

forever
  if camera sees "brick_2x4"
     with confidence > 50%
    move arm to pose PICKUP
    close gripper
    wait 1 second
    move arm to pose DROP_ZONE
    open gripper
Browser-runner is a genuine contribution: normally a block change = recompile + reflash (slow). Our JS interpreter walks the live blocks and streams servo commands over the same WebSocket, so iteration is instant. Also note we dropped Blynk entirely — no cloud.

How we got there — the optimization log

ProblemFixOutcome
Servos buzz/jam into end-stops; MG996R overheats (~2.5 A stall) Narrowed PWM range 100–500 → 150–450 countsNo end-stop stalling; rail stopped sagging
All 5 servos start at once → ground bounce → board resets Move one joint per tick (serialized slewer, configurable order)Resets eliminated
Gripper stalls on object → starves shoulder Tuned CLOSE angle per piece width (10/13°, not 0°); travel cappedShoulder lifts freely; drove the 92.5% (SO3)
Servo spikes couple into ESP32 logic rail Separate 5V/3A servo supply via PCA9685 V+No further spurious resets
Browser blocks direct cam fetch (CORS) Backend /capture proxy (+ server-side rotate)Frames & boxes align, no CORS errors
This is Table 6.8 condensed — the "we actually engineered this" slide. IMPORTANT honesty: the gripper fix is an ANGLE + travel-cap strategy (set close angle so the servo reaches target instead of stalling), NOT electrical current sensing. There is no ADC on the servo line. If asked "how do you detect a stall?" — we don't measure current; we avoid commanding a stalling angle. The ~2.5 A figure is the MG996R's stall current we observed, not a live reading. The paper (SO3) states the 92.5% sorting rate "was driven by mechanical tuning of the gripper CLOSE angle and calibration of the pick/place poses" — so this row is the direct cause of the headline result. Close angles are per width: narrow 10° (1-stud), wide 13° (2-stud). The serialized slewer moves one joint per tick in a configurable order; note it is NOT soft-ramping (that's listed as future work) — it's fixed-step, staggered to kill the current surge.

Future work
